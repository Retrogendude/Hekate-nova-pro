# Hekate Nova Pro 29 — pairings, SD save and reconnection

Formatting the SD card is not a fix for the observed problem.
The pairing data are read in the Joy-Con. v28 received both
controllers on one OLED, while R lost its connection on the other.
Going through Nintendo restored the import 2/2; a new trial then
reproduced 0/2 on the second OLED. The exact cause on hardware remains to be verified.

This version accepts the two host profiles already validated by the BDK reader:
Nintendo and standard. v28 required the Nintendo classification even for a
standard record recognised as valid. The new path keeps the
checksum check, the active entry, the non-zero keys, the sides and the
compatibility of the two hosts. The truncated SPI responses no longer fill
the cache. The historical Hekate export keeps its Nintendo classification.

The timeout of a connection attempt goes from 15.36 s to 5.12 s. The attempts
continue, spaced, as long as the Bluetooth service is enabled; they no longer
stop at the third failure. Only one outgoing attempt remains active
at a time. A restored connection resets the recovery counter to zero.
This improves the recovery after waking or a cut; waking with a normal button
and the absence of cuts on both consoles still have to be tested.
The radio rate, the encryption, the channel management and the keys are kept.

Two new actions appear in the Wireless Joy-Con menu:

- **Save the pairings**: after a valid read, Bluetooth stopped.
  A 72-byte file contains the necessary data of both controllers,
  in `bootloader/bluetooth/joycon-pairing.bin`. It is not a complete copy
  of the memory of the Joy-Con. The keys are saved in clear text:
  keep this file private and do not send it with the reports.
- **Load the pairings**: explicitly reloads this file into the
  session after a restart. A format or checksum error makes it
  rejected, keeping the keys already present in memory.

The save uses a temporary file then keeps the previous version
in `joycon-pairing.bak`. The load tries this copy if the main file
is absent or damaged. The `.bak` file also contains private keys.
A save with a single valid controller remains a 1/2 save.
"Clear the keys" clears the session in memory, not the save files.
The files are to be used with the associated controllers. To compare the
two consoles, read and save the pairings corresponding to each trial.
If a new pairing is made in the Nintendo system, read again then
save the updated data before reusing the SD save.

Installation and check:

1. Extract the ZIP to the root of the SD, replacing `bootloader`, without formatting.
   Use `hekate_nova_pro_6.5.5_v29.bin` if necessary, then restart.
2. With the Joy-Con attached, read the pairings. If 2/2, save them before
   enabling Bluetooth. If 0/2 persists, stop and recover the report.
3. Detach the controllers, enable Bluetooth and try first a normal button
   of each controller to wake them up. Test the movement and A/B.
4. Stop Bluetooth and immediately recover `bootloader/bluetooth/last-session.txt`,
   without clearing the keys nor reading the pairings again. Do not attach the pairing
   files `.bin` or `.bak`.
5. To check the persistence: restart Nova, load the pairings from
   the SD, then redo the test. No reading of the rails is necessary for
   this load if the save is valid.

The report adds `recognized` (valid profile recognised) and `source` (1 rails,
2 SD). During an SD load, the Nintendo classification is not filled in;
the rail indicators do not represent a new physical read.
The trace type 20 indicates the requested attempt timeout, in Bluetooth units.
No key, address or raw data is added to the report.

Compilation and checks on PC do not replace the hardware validation.
The recovery after a timeout is tested with a simulated radio; it does not
prove that the cause of the R cuts has disappeared. No erasure and no
new pairing is sent to the Joy-Con. Base: Hekate6.5.5 / Nyx1.9.5.
The user settings are not included in the ZIP. Licences kept.
